# XL004 — text-in-numeric-cell

**Severity:** ERROR  
**Confidence:** CERTAIN  
**Requires:** CACHED_VALUES, NUMBER_FORMATS

The cached value is a string and the cell's number format is numeric or
currency.

## Two branches, and they are not the same defect

Excel stores an error as a string, so `#DIV/0!` and `"not applicable"` are
both text to a naive check. Reporting them identically gave the commonest real
defect in a workbook — a broken formula — the diagnosis and remediation of a
formatting problem. The rule distinguishes them, and the `kind` evidence key
records which branch fired.

| `kind` | Condition | Message | Remediation |
|---|---|---|---|
| `error` | The value is exactly one of the Excel error literals **and** the file corroborates it: the cell is a formula, or Excel typed it `e` | `cached error <value> in a numeric-formatted cell` | Repair the formula, or handle the error case so the cell holds a number |
| `text` | Any other string | `text value in a numeric-formatted cell` | Move status text to a status column and keep the numeric cell numeric |

The corroboration matters. Matching the literal after `.strip().upper()` would
add matches the file does not claim, and did: the ordinary text `" #n/a "`
was reported as a broken formula.

## Fixtures

- `kind = "text"` — `E12` formatted `$#,##0` with cached text `N/A - no load`.
- `kind = "error"` — a currency-formatted cell whose formula cached `#DIV/0!`.
- Neither — the text `" #n/a "` typed as a string, which must report `text`.

## Open question, not settled by this rule

`GOAL.md` rule 4 says error states may "use real Excel error handling," which
arguably makes a bare `#DIV/0!` compliant. This rule corrected the *wording* of
the error branch; it did not decide *whether* the branch should fire at all.
Whether an unhandled error is its own rule needs an ADR.
